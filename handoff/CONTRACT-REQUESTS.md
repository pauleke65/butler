## 2026-10-06 Workstream A (Platform & Policy): rules, wrapper, executor, local gateway, debug API

Everything below is already worked around in code; the integrator should fold the ones marked **[contract]** into `01-contracts.md`.

1. **[contract] §9.3 `spend_cap` compiles to ONE policy** with `action in [<tool>, <tool>]` (one tool: `action == …`), not "one forbid per tool". Reason: one Rule = one AgentCore policy (create_policy takes a single statement) = one `@id("<rule_id>")`. Semantics are identical (parity-tested).
2. **[contract] §9.3 resource clause is `resource is AgentCore::Gateway`** in every forbid (same as the §9.2 base permit), not `== AgentCore::Gateway::"<arn>"`. If the ARN placeholder were wrong a forbid would silently never match (fail open). `Identities.gateway_arn` is used only for the entity id in local evaluation and by `AgentCorePolicyService`.
3. **[contract] §9.3 type confusion fails open in Cedar.** Guards (`has`) handle *missing* fields, not *wrong types* (`"6000" > 5000` errors, the forbid is skipped, base permit allows; verified with cedarpy in `libs/butler_rules/tests/test_failopen.py`). Mitigations implemented: `butler_rules.policy_field_problems(args, tool)` makes the wrapper and the local gateway fail closed (`INVALID_INPUT`, no Gateway call) on missing/mistyped `amount_minor`, `category`, `event_owner`, `recipient_*`. **Request for P-2:** register the Gateway inline schemas with these fields `required` and typed exactly (`integer`/`string`/`array<string>`, `additionalProperties` as strict as the tools allow), and keep the Lambda re-validation (§7).
3b. **[contract] `never_contact` only matches `recipient_contact_ids`.** Emailing the same person through a raw `recipient_email` is covered only by `ask_non_contact` (agent only), so an approved non-contact email to the boss's address would pass the executor. Suggest: `never_contact` params gain optional `email`, and the Cedar adds `|| context.input.recipient_email == "<email>"` (guarded). Not done: the contract fixes the params.
4. **[contract] §8 wrapper additions** (all additive): `call_action(..., guard: RunGuard | None, undo_of: str | None)`; `ActionOutcome.error: {code,message} | None` (codes `DENIED_RETRY_BLOCKED`, `INVALID_INPUT`, Lambda codes); the wrapper also adds `correlation_id`, `plan_id`, `need_id` to the Gateway args (the tool schemas require `correlation_id`); default `idempotency_key` = `${plan_id}:${need_id}:${action_kind}:${hash(args)}` (hash instead of a counter so a retried identical call gets the same key); `reasoning` is sanitised (`clean_reasoning`) because it is model-written.
5. **[contract] `GatewayClient.call` gets an optional keyword `household_id`** (sent as `X-Butler-Household`, local only). The wrapper passes it only when the client's `call` signature accepts it, so plain fakes `call(principal, tool, args)` keep working. `HttpGatewayClient` defaults the household from `HOUSEHOLD_ID` (default `hh_demo`).
6. **Receipts are written for every tool call, including read-only ones** (`search_products`, `search_providers`, `list_events`, `get_weather`), as §8 says "always". `list_actions` / ledger / the Black Box will therefore show searches unless C filters them: `butler_actions.summaries.READ_ONLY_TOOLS` is the list. Request: decide whether §3.5 should exclude read-only tools.
7. **§6 executor behaviour fixed where the contract was silent:** approving an already-`executed` decision returns `ok: true` with the original receipt and `replayed: true` (executes once); other non-pending statuses return `INVALID_INPUT`. A `never`-rule denial returns `BLOCKED_BY_NEVER_RULE`, decision → `failed`, need → `skipped` ("Not allowed by your rule: …", per loop rule 2) rather than `blocked`. Failure responses also carry `data: {decision, receipt}` so the server/views can show the blocked receipt. Undo returns `NOT_REVERSIBLE` for `send_email`, for already-undone receipts and for receipts without the provider id needed to reverse them.
8. **§11 debug API:** `/receipts?since=` returns receipts with `action_id > since`, so a later status change (`undone`) of an old receipt is not re-sent; the panel should re-fetch `limit` rows occasionally. `/policy-events` returns the generated `PolicyEvent` model (adds `action_id`, `rule_texts`, `amount_minor` to the §11 sketch). Debug API is also usable as a Function URL Lambda via `debug_api.core.lambda_handler`.
9. `draft_to_rule(draft, household_id, *, origin, now, ids=None, rule_id=None)`: `ids` (needed to compile Cedar; defaults to `Identities.from_env()`) and `rule_id` are extra keywords. The template decides `effect` (the model's `effect` is overridden). `never_contact` accepts an optional display-only param `contact_name`.
10. Root `pyproject.toml` now lists `debug-api` as a uv workspace member / test path (package `butler-debug-api`), and `libs/butler_actions` depends on `butler-rules` (the wrapper uses the matcher).


## 2026-10-06 Workstream B (Agent & Actions): action handlers, agent, drafters, evals

1. **[contract] §7 household for the Lambdas.** The tool input never carries a household (§1), but the handlers need one for contacts and `ORDER#/BOOKING#/EVENT#` records. `dispatch(tool, event, *, store, now=None, adapters=None, household_id=None)` takes the household as a keyword (the local gateway already passes it). In AWS the Lambda should be deployed with `HOUSEHOLD_ID`.
2. **[contract] §7 tool outputs, additive:** `search_products` products also carry `delivery_label` (e.g. "Friday 12-2 PM"); `deliver_by` is a hard filter on the ETA (end of the delivery window), so late items are *absent* (the planner makes a second unfiltered search to document why a late option was rejected). `search_products` ranks by query-token hits plus a bonus when a bundle's size ("for 7", "3 people") covers the number in the query, then price. `search_providers.date` means "needed by": slots after the end of that day are dropped; `window` is `morning|afternoon|evening`. `send_email.sent_to` is first names (contact path) or the address (`recipient_email` path). `checkout` also rejects `merchant` that does not sell every SKU and an ETA after `deliver_by`.
3. **[contract] §7 `recipient_email` is `UPSTREAM_UNAVAILABLE`, not `INVALID_INPUT`,** when SES sandbox rules forbid the address (per ticket A-1). Allow-list = saved contacts' emails + env `SES_ALLOWED_RECIPIENTS`; `SES_SANDBOX=false` lifts it.
4. **[contract] §5 `apply_rule` replacement link.** `apply_rule` only receives `rule_id`, but a changed rule must disable the old one *after* the new one is active. `draft_rule` with `base_rule_id` stores a side record `RULECHANGE#<new_rule_id> = {"replaces": "<old_rule_id>"}` (via `Store.put_record(hh, "rulechange", ...)`), which `apply_rule` reads. Suggest adding `replaces_rule_id?: string` to `Rule` instead. `apply_rule`'s `POLICY_PROPAGATING` and policy failures return the envelope with both `error` and `data: {rule}`.
5. **[contract] §5 Plan status** after a run: `waiting_on_you` if any need is `needs_you`; `complete` if every need is `done`/`skipped`; otherwise `active` (any `blocked` or `doing`). All needs end in a terminal state (never `doing`): a crash, the 25-step cap or the 120 s cap marks leftovers `blocked` ("Ran out of time; ask me to try again.").
6. **§5.1 code-enforced rule 2:** if the (LLM) planner leaves a need `doing` after an ask-first DENY, the run end creates the `approve_action` decision itself (option = the denied action, `reason_held` = the matched rule); after a `never` DENY it marks the need `skipped`. Idempotency keys are deterministic (`${plan_id}:${need_id}:${kind}:${n}`), so a re-run replays instead of repeating side effects.
7. **Preferences (A-10)** use keys `merchant:<category>` (value = merchant) and `provider:<service_type>` (value = provider name), noted after executed checkouts and, in `resume_plan`, after an executed approved decision. With no stored preference the scripted planner derives the merchant from past executed orders ("history: 3 earlier drinks orders from FreshCart"). Preference shown in `context_used` as `preference: FreshCart for drinks`.
8. **For Workstream A / contract §8 (not changed by B):** (a) golden step 2 expects the 4200 drinks receipt "ALLOW by `rule_default_spend`", but the wrapper stores `authority.rule_ids = []` for ALLOW decisions (only the spoken summary cites the spend limit text). ## 2026-10-06 · Workstream D (simulator) · notes and requests

No change to wire shapes is required to ship the simulator. The items below are things other workstreams should know, ordered by risk.

1. **Elicitation cannot work on a stateless MCP server (relevant to S-2, contracts §3.7 step 3).** Verified with `@modelcontextprotocol/sdk` 1.32: a server built per request (stateless Streamable HTTP, as the Butler server and AgentCore expect) never sees `initialize`, so `server.elicitInput()` fails with "Client does not support form elicitation" even though the simulator declares `elicitation: {form:{}, url:{}}`. It also needs `{ relatedRequestId: extra.requestId }` so the request rides the tool call's own SSE stream rather than the standalone GET stream. **Workaround / recommendation:** keep the two-step `confirm` flow in §3.7 as the only path (it is what the golden demo uses); treat elicitation as optional. The simulator's brain supports both (binds "yes" to `structuredContent.needs_confirmation`).
2. **Convention the simulator's offline brain relies on (no change, please keep):** `structuredContent.needs_confirmation: true` (§3.7), `structuredContent.pending_decisions[0].kind === "approve_action"` (§3.3), and `structuredContent.error = { code: "AMBIGUOUS_REFERENCE", candidates: [{id,label}] }` (§14). Also `spoken_summary` (§3.1) is what gets spoken, and `answer_decision` must accept the literal choices `"approve"` / `"reject"` and option title text such as "BrightHome" (§3.4).
3. **`scripts/butler-golden.yaml` asserts these shapes; confirm they match what the server returns:**
   - `list_rules` returns `ask_first[*].rule_id` including the new rule (used to wait until the rule is active);
   - `list_actions {period:"this_week", filter:"blocked"}` includes `held_for_approval` receipts with `authority.decision = "DENY"` (used to wait for the DENY in scene 7);
   - `list_actions` receipts carry `cost.amount_minor` (4200 for the drinks, 8500 for BrightHome), `authority.rule_ids`, and a `title` containing "BrightHome" for the booking;
   - `explain_action` receipt `alternatives[*].option` mentions "BudgetBasket" and "Corner Cellar", and `alternatives[*].rejected_because` mentions "Saturday" and "50 dollar";
   - `get_plan {plan_id}` (§3.11, app-only) is callable by the simulator over plain MCP and returns `plan.needs[*].status`;
   - `handle_situation` result includes `plan.plan_id`; the away plan's `pending_decisions[0].reason_held.rule_id` equals the new rule's `rule_id` returned by `object_to_action {confirm:true}`.
4. **ext-apps version.** The simulator pins `@modelcontextprotocol/ext-apps@^1.7.5` and `@modelcontextprotocol/sdk@^1.32.1`, the same as `server/package.json`. ext-apps 2.x requires the MCP SDK v2 packages (`@modelcontextprotocol/client|core|server`), so do not bump one side only.
5. **Debug API (§11).** The Black Box panel calls `GET /receipts?limit=50&since=<last action_id>` and `GET /rules` every second with `Authorization: Bearer <DEBUG_API_TOKEN>`. It goes through the simulator's same-origin proxy, so the debug API does **not** need CORS headers. It expects receipts newest last, ULID `action_id`s, and `rules[].active` / `policy_status`.
6. **Auth.** X-2's "Cognito client credentials" is implemented generically as OAuth2 client credentials (token URL, client id/secret, optional scope, HTTP basic auth, cached and refreshed before expiry). Tested against a local token endpoint only, not a real Cognito pool. If the Cognito app client needs the credentials in the body instead of basic auth, tell Workstream D.


## 2026-10-06 Workstream C (MCP server and views)

All worked around in `server/`; fold the **[contract]** items into `01-contracts.md`. SDK in use: `@modelcontextprotocol/sdk` 1.32.1 + `@modelcontextprotocol/ext-apps` 1.7.5 (the v2 split packages `@modelcontextprotocol/server|client|core` exist; ext-apps 2.x needs them).

1. **[contract] §3.1 error envelope gains `spoken_summary` and optional `error.details`.** `structuredContent = { ok:false, spoken_summary: <message_spoken>, error:{ code, message_spoken, candidates?, details? } }`. `spoken_summary` lets a host that only reads that field speak the error; `details` is a short non-spoken string (zod issue text) so the calling model can self-correct on `INVALID_INPUT`.
2. **[contract] §3.1 `outputSchema` must accept the error envelope.** The SDK client (and likely Alexa's) validates `structuredContent` against `outputSchema` even when `isError: true`. The server advertises `outputSchema = { type:"object", oneOf:[<success schema>, <error envelope schema>] }`. If the integrator regenerates JSON Schemas from zod, add a `ToolErrorEnvelope` schema with `ok: false`, `spoken_summary`, `error: ToolError (+ details?)`.
3. **[contract] §3.2 service needs start as `doing`, not `needs_you`.** `ScriptedPlanner` (and the §5.1 loop: "work need by need") only processes `doing` needs; a need that starts `needs_you` without a decision is skipped, so no cleaner decision is ever created. The server writes services as `doing`; the agent flips them to `needs_you` via `request_decision`. `handled_by_butler` / `needs_you` are computed by capability (a `doing` services need already counts as needs-you), and the spoken summary still says "I'll check with you on cleaning".
4. **[contract] §3.7 POLICY_PROPAGATING is returned as a success.** `object_to_action {confirm:true}` / `change_rule` return `ok:true` with the rule (`policy_status: "creating"`) and spoken "Done. It'll take effect in a moment." (an `isError` result would make the Alexa brain apologise for something that worked). The code stays in the table for the agent.
5. **[contract] §10 `DRAFT#LATEST` lock carries additive fields** `intent: "new" | "replace" | "remove"` and `replaces_rule_id` inside the `data` JSON (the Python reader only reads `rule_id` / `expires_at`; the agent's own `set_latest_draft` call is overwritten by the server after `draft_rule` returns). Used so `change_rule` confirm knows whether it is a replacement or a removal. `expires_at` is epoch seconds (as `store.py`).
6. **[contract] §3.5 read-only tool receipts are excluded** from `list_actions`, `get_ledger_page`, ranking and reference resolution (`Calendar___list_events`, `Supplies___search_products`, `Services___search_providers`, `Context___get_weather`), per the lead's note on A's wrapper. `period: "this_week"` means the last 7 days.
7. **[contract] §3.10 / §6 undo response.** The server accepts `{undo, original}` (what `butler_executor` returns) or `{receipt}`. Please pin `{ original: Receipt, undo: Receipt }` in §6.
8. **[contract] §4 views use a small in-repo bridge instead of `App`.** Importing `App` from ext-apps costs 445 KB per view (MCP SDK schemas + zod), over the 200 KB limit; `server/ui/src/bridge.ts` speaks the same wire protocol (protocol 2026-01-26, `ui/initialize` handshake, tool-result / host-context notifications, `tools/call`, `ui/request-display-mode`, `ui/message`). Validated against the real `AppBridge` (host side) in the fixture preview. Views are 27-34 KB.
9. **[contract] §3.3 `answer_decision` reject/failed side effects are done by the server** (decision -> rejected, need -> skipped "You said no.", plan `updated_at` bumped; on executor transport failure the decision is moved `pending -> failed` and the need -> `blocked`). A `BLOCKED_BY_NEVER_RULE` executor error is passed through untouched (the executor already set decision `failed`, need `skipped`, per A's item 7).
10. **Plan/decision timestamps written by the server are UTC with `+00:00`** (same as `clock.iso()`), so `GSI1SK` values from both languages sort lexicographically. User-facing `starts_at` / `ends_at` use the household timezone offset.
11. **`ToolError.code` for unrecognised `answer_decision` choices:** `NOT_FOUND` with the options as `candidates` for `choose_option`, `INVALID_INPUT` for `approve_action` (spoken: "Should I go ahead, or skip it?").
12. Suggestion for `packages/contracts`: export `ListActionsFilter` / `ListActionsPeriod` enums (the server mirrors them as string literals) and a `ToolErrorEnvelope` (see 2).
